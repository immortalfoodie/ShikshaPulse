# ShikshaPulse — from education data to accountable action

**AI Foundation Hackathon · District education diagnostic & action platform**

Block and district education officers get assessment results that say *"you are near the bottom"* and nothing else. The data that could explain why (attendance, UDISE+ infrastructure, teacher vacancy, election duty) sits in separate files with different keys and formats. Collating it takes days, so remedial effort rests on instinct, and nobody owns the follow-up.

ShikshaPulse turns that into one loop:

```
Data → Diagnosis → Decision → Action → Accountability → Outcome
```

| Problem in the scenario | What ShikshaPulse does |
|---|---|
| Files don't join (school code vs month vs separate file) | AI column mapping, UDISE-code master registry, name matching, review queue |
| Every year has a different format ("another week") | Format-agnostic normalisation → 3-year warehouse in **~6 seconds** (measured, 13 files · 1,168 schools) |
| "Have we fallen or were we always here?" | 3-year trend on comparable instruments only, with instrument changes flagged |
| "Something caused this" (but what?) | Evidence-graded signals (HIGH/MEDIUM/CONTEXT/INSUFFICIENT) — association, never causal claims |
| "It was an election year" (vague) | Peer benchmark: similar election-affected blocks in **other districts** |
| Blocks targeted by instinct | *Instinct vs Evidence* view + Intervention Radar (multi-indicator, with reasons) |
| No clear responsibility | Action Room: owner, deadline, evidence, verification, audit trail |
| Did it work? | Implementation (was it done?) and learning (did outcomes move?) tracked separately |
| Problems found only a year later, when NAS results arrive | **Early warning:** each month, compares the last 3 months with the same months last year (attendance drops, teacher-attendance dips, missing reports) |
| Data cannot show what happens inside the classroom | **CRC school-visit checklist:** 6 Yes/Partly/No questions on a phone, works offline, and feeds the Why? page |
| "Which action actually works?" | Every drafted action shows its **track record** elsewhere. Vacancies get concrete **teacher-sharing pairs** between nearby schools |
| Monthly review meetings ramble | **Review meeting mode:** 6 guided steps that end with decisions saved as owned tasks |
| Parents and SMCs never see the data | One-page **school report card** in plain words, which can be printed or shared on WhatsApp |

## Built for village schools, not just district offices
- **Six languages, end to end:** English, हिन्दी, मराठी, বাংলা, தமிழ், తెలుగు. The first screen asks for a language. Every label, ⓘ explanation, chart caption, reason and AI answer appears in that language. AI answers work in all six languages **even with no API key**, through the offline engine's phrase tables.
- **Read-aloud and voice:** a 🔊 *Listen* button on summaries, answers and the "My school" page (Web Speech, with `hi-IN`, `ta-IN` and so on). Questions can be spoken into a 🎤 mic wherever the browser supports speech input.
- **"My school" view** for headmasters and teachers (persona *Shanti Devi*):
  - four big cards in plain words, e.g. "40.4% — 19.5 points lower than 2022-23"
  - where the school needs help
  - one-tap *I have started* / *Done — send for checking* buttons
- **School visits for Cluster Resource Coordinators** (persona *Meena Kumari*):
  - a phone-first checklist with big Yes / Partly / No buttons
  - **works with no network**: visits are saved on the phone and sent automatically when the signal returns, with no duplicates
  - the app can be installed on a phone's home screen (PWA)
- **School report card** for parents and School Management Committee meetings: one page, printable, read-aloud, and shareable on WhatsApp.
- **ⓘ everywhere it matters:** every metric, evidence strength, finding label, radar rule, task status and model, plus a collapsible *How to use this page* strip on each page.
- **Text size control** (A / A+ / A++), large touch targets, keyboard focus rings, and colour never used alone (arrows, signs and labels always accompany it).
- **Design:** a warm civic palette (forest green, saffron, brick on paper), with no blue, no purple and no gradients. Fonts are *Mukta* and *Noto Sans* for Indian scripts. Chart colours were checked with a colour-blindness validator (green `#1f7a4a` / saffron `#dd8f22`, CVD ΔE 16.4).
- Translations are machine-assisted and **must be reviewed by native speakers** before official use; the UI says so.

> **All demo data is SYNTHETIC** (generated by the Scenario Lab). No real schools, students or officers. The UI shows a banner whenever synthetic data is loaded.

```bash

```

### Turning on the LLM (free tier)
Without a key, everything runs on the **deterministic engine**: same tools, same guard, template-written answers in all six languages. To use a free LLM, edit `backend/.env`:

```
LLM_PROVIDER=gemini
LLM_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai/
LLM_MODEL=gemini-2.5-flash
LLM_API_KEY=<free key from https://aistudio.google.com/apikey>
LLM_API_KEY_FALLBACK=<optional second key, e.g. from another Google account>
```
Groq (`llama-3.3-70b-versatile`) and local Ollama also work; see `.env.example`. Restart the server after changing `.env`.

Live Gemini has been verified: answers pass the guard (e.g. 19/19 numbers). The free tier sometimes returns *503 high demand*; the client retries within a time budget (about 35 s per question, with a 20 s limit per call). If it still fails, the deterministic engine answers, so the demo never hangs or breaks.

**Fallback key.** If `LLM_API_KEY_FALLBACK` is set and the primary key is rate-limited (429), over quota, rejected (401/403) or the provider is overloaded (5xx), the same request is retried at once on the fallback key. The failed key rests for a cooldown (60 s for rate limits) so later questions go straight to the healthy key. If both fail, the offline engine answers. `GET /api/llm/status` shows `keys_configured`, `active_key` and `key_switches` (never the keys).

## 5-minute demo script

1. **Sign in as Mr. Chan.** The Command Center shows Devgarh is **4th of 4 districts** on foundational numeracy, with numeracy down 6.7 pp over three years. The trend answers "have we fallen?" (yes; this is not a long-standing level).
2. **Data Studio → Analyse with AI → Build 3-year warehouse.** 13 messy files: a different format each year, wide month columns, raw marks out of 50, and misspelt names without codes. They are joined in about 6 s (measured on a laptop), against the scenario's "3–4 days + another week". 26 uncertain matches wait in **Records requiring verification**; nothing is silently guessed.
3. **Instinct vs Evidence.** Pick Poti and Sinda (the officer's instinct). The evidence points to **Kerwa**: the steepest decline, 16 pp below what its conditions predict, and not explained by any tracked indicator.
4. **Why? (evidence graph).** Poti: maths-teacher vacancy rose from 10% to 45% (HIGH signal). Sinda: attendance fell 15 pp in migration months (HIGH). Kerwa is an *open question*. Election duty appears as *context*, not a cause. Click any signal to see its evidence: source files, period, affected schools.
5. **Peer Benchmark (Poti, election-only).** 5 similar election-affected blocks in other districts changed by −5.1 to −2.5 pp; Poti changed by −13.6 pp. The election alone does not match the size of Poti's decline.
6. **Intervention Radar → Draft actions.** The AI drafts actions from the intervention library, such as temporary maths-teacher redistribution for the schools with vacancies. Assign one to **Romi (BEO Poti)** with a deadline.
7. **Switch persona → Romi.** Romi records implementation (posts filled), attaches evidence and submits it for verification. **Switch back → Mr. Chan verifies.** The Action Room also shows simulated history: an action that was implemented and improved outcomes, one implemented with no change yet, one never implemented (Kerwa), and one overdue.
8. **Ask a question** (any of the six languages, typed or spoken): *"Why did numeracy fall in my district?"* The answer carries **✓ Numbers verified against source calculations (34/34)**, evidence chips, and labels (fact / signal / open question).
9. **Meeting Brief → PDF.** A one-page review brief with owners and deadlines.

**Field features (2 more minutes):**

10. **Overview → Early warnings.** In the last 3 months, attendance fell 8+ pp in a share of schools compared with the same months last year. The alert appears months before the next assessment would show it.
11. **Sign in as Meena Kumari (CRC, Kerwa).** Her home page is *School visits*. Turn off the network, fill the 6-question checklist and save: the visit shows *Saved on this phone*. Turn the network back on and it syncs by itself.
12. **Why? → Kerwa.** Kerwa was an open question. It now has a *From school visits* card: teaching materials and level-grouping are rarely seen in the classrooms. Data from the field fills the gap left by the files.
13. **Block → Poti.** *Teacher sharing options* pair a school with no maths teacher with a nearby school that has spare capacity. Draft actions show *Past results*, e.g. how often teacher redistribution was implemented elsewhere and the average change that followed.
14. **Review meeting.** Step through standing → early warnings → overdue tasks → blocks → decisions. Each decision becomes a task with an owner.
15. **School report card.** From any school, open a one-page card for parents and share it on WhatsApp.

## How AI is used (and kept honest)

| Where | What the AI does | Safeguard |
|---|---|---|
| Data Studio | Resolves ambiguous column headers from samples (dictionary → fuzzy → value-profiling → **LLM**) | Every mapping shows its method and confidence, and the officer can override it |
| School matching | Normalises names and matches by distinctive tokens and fuzzy scores | Below the confidence threshold or ambiguous → human review queue |
| Why? engine | Pooled first-difference regression + within-block association → evidence-graded signals | Labelled as association. Coverage < 60% → INSUFFICIENT EVIDENCE |
| Expected vs Actual | Ridge model predicts the score from *conditions only* | No outcome (current or lagged) used as input; block-grouped cross-fitting |
| Peer benchmark | k-nearest neighbours on baseline characteristics, optional election filter | Shows the peer range and median, not a verdict |
| Ask ShikshaPulse | LLM calls **12 vetted analytics tools** (no raw SQL), then writes a structured, cited answer | **Evidence Guard**, below |
| Early warning | Same-months-last-year comparison of monthly attendance and teacher attendance; can be asked in any language ("any early warnings?") | Thresholds stated in each alert; schools that stopped reporting are surfaced as their own alert, not hidden |
| Field observations | Aggregates CRC checklist visits into practice-level percentages that join the Why? evidence | Shown only with 3 or more visits; labelled as observation and never mixed with test scores |
| Action drafting | Picks interventions for the detected signals; the LLM writes the rationale | Rationale numbers must match the evidence; causal wording softened; officer edits and assigns |

**Evidence Guard** (`backend/app/ai/guard.py`):
1. Every number must match a value in the tool outputs, within a rounding tolerance.
2. Every finding must cite existing evidence ids and a reporting period.
3. Findings are labelled *observed fact / associated signal / open question*. A finding that cites a signal cannot be presented as a fact.
4. Causal wording ("caused", "due to", "led to", "के कारण") is rewritten to associative wording.
5. Insufficient, conflicting or unexplained evidence is always surfaced. The guard adds anything the model omitted and says so.
6. If the answer fails, the model gets one retry with the guard's feedback. If it fails again, the deterministic engine answers.

The badge certifies the numbers and citations, not that every interpretation is proven.

## Evidence that it works — `python -m eval`

The evaluation suite (`backend/eval/`) generates four scenarios (one demo scenario, plus three **randomised** ones that place effects on random block names), runs the full pipeline in isolated warehouses, and scores the results against each scenario's `expected.json` ground truth. The latest run passed **47/47 checks**; see `backend/eval/report.md`.

| Metric (latest run) | Result |
|---|---|
| School-match precision | 0.995–1.0 |
| Auto-match recall (name variants without codes) | 0.92–0.95 |
| Planted-signal detection recall | 0.86–1.0 |
| False adverse flags on blocks without that effect | 0 per block |
| Block status accuracy (insufficient / non-comparable / unexplained / stable / improving) | 1.0 on all four scenarios |
| Expected-vs-actual held-out R² (block-grouped) | 0.55–0.70 |
| Guard catches adversarial answers (invented number, causal claim, missing / fabricated citation, mislabelled signal, omitted open question) | 6/6 |
| Fallback answers fully grounded (EN + HI) | 9/9 |
| Data-confidence score falls as missing data rises | yes (99 → 94 → 88) |

Known miss, reported honestly: in the demo's Chitrangi block, three overlapping effects mask the smaller infrastructure signal.

Unit tests: `cd backend && .venv/Scripts/python -m pytest -q` (33 tests, including task and match-review access rules, primary → fallback key switching, grounded answers in all six languages, early-warning detection of the planted attendance drop, idempotent offline visit sync, and valid teacher-sharing pairs). These include a scripted-LLM test in which the model invents a number, the guard rejects it, and the retry passes.

## Deploy (public demo link)

ShikshaPulse runs as **one container** that serves both the API and the React app on one URL (`Dockerfile`). Vercel alone is not a good fit:
- The backend needs pandas, numpy, SciPy and scikit-learn (about 460 MB installed).
- It keeps a SQLite database and runs data rebuilds as background jobs, which serverless functions do not support.

A Vercel + Render split is possible, but it adds a second URL and cross-origin setup for no gain, since the backend already serves the frontend.

**Recommended: Render (free Docker web service)**
1. Put the project on GitHub. `.gitignore` already keeps `backend/.env` out.
2. In Render, choose **New → Blueprint** and select the repo. `render.yaml` creates the service.
3. In the service's **Environment**, paste `LLM_API_KEY` and, optionally, `LLM_API_KEY_FALLBACK`. `APP_SECRET` is generated for you, and `PUBLIC_DEMO=1` is already set.
4. Open the `onrender.com` URL. The image builds the demo data during the build, so the app starts in seconds.

Free-tier behaviour:
- The service sleeps after 15 idle minutes, and the first visit after that takes about a minute. Open the link a few minutes before judging.
- Restarts reset the demo to its seeded state. Tasks or visits added during a session do not survive a restart, which is acceptable for a demo.

**Alternative: Hugging Face Spaces (Docker)** gives more memory and sleeps only after 48 hours idle. Create a Docker Space, push this repo, add `app_port: 8000` to the Space README front matter, and add the keys as Space secrets.

**`PUBLIC_DEMO=1`** keeps a shared link consistent for every visitor:
- Scenario Lab generation is off.
- Records can be rebuilt only from the demo files. Uploads can still be read and previewed.
- Uploads are capped at 15 MB.

Run locally, without the flag, for the full toolset. Measured locally: peak memory about 300 MB, cold start about 5 s from the pre-built data.

## Data tiers and the path to real deployment

| Tier | Source | Status |
|---|---|---|
| `synthetic_demo` | Scenario Lab | This build. Bannered everywhere, never presented as real |
| `department_uploaded` | Files uploaded in Data Studio by an authorised officer | Works now (Data Studio → Department file upload) |
| `verified_official` | Authorised API integrations | Adapter stubs document the requirements |

We do **not** assume public APIs expose every field we need. For example, subject-wise vacancy and monthly attendance are usually *not* in UDISE+. Each stub (`app/sources/udise_api.py`, `state_portal.py`) lists the authorisation, fields, historical coverage and refresh frequency it requires.

Switching tiers is configuration only (`config.yaml` → `mode: demo | department`); analytics and the UI don't change. ShikshaPulse is designed to **sit on top of** UDISE+, Vidya Samiksha Kendra (VSK) and NDEAR-style registries as a decision-and-action layer, not to replace them.

Before handling real or student-level data, the deployment needs:
- encryption at rest and in transit
- a retention policy
- aggregation by default
- a review against the **DPDP Rules 2025**, in addition to the RBAC and audit logging already built

The current build contains no student-level data.

## Limitations
- All findings are associations from observational, school-level aggregate data. Classroom practice enters only through CRC visit checklists. Where there are fewer than 3 visits, unexplained declines stay *open questions*. Demo visits and the demo action history are simulated and badged.
- Synthetic base rates are loosely calibrated to published NAS 2021 / UDISE+ ranges but are not real measurements.
- The live LLM path is tested with a scripted model in pytest and has been verified with a free Gemini key. Without one, the deterministic engine answers through the same tools and guard.
- Offline support covers the visit form (it queues on the phone). The dashboards need a connection.
- Teacher-sharing suggestions use maths-teacher counts and pupil load only. Distance and travel time are not in the data, so pairs in the same cluster are preferred as a proxy.
